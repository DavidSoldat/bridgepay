# BridgePay — Credit Risk Engine

Standalone scoring service. Loads a scikit-learn pipeline exported to ONNX
plus a `coefficients.json` explainability sidecar, exposes
`POST /internal/score`, and internally calls the Mock Credit Bureau and
Repayment Reconciliation Service to assemble the feature vector it scores
(spec section 11's orchestration decision — this service owns those two
calls, not Application Service).

## Run locally

```bash
docker-compose up --build
```

Uses the `local` Spring profile (JWT auth disabled) and starts a Redis
container for the score cache. The trained model (`model.onnx` +
`coefficients.json`, produced by `scripts/train_model.py`) ships in
`src/main/resources/model/`. Run standalone like this, the Mock Credit Bureau
and Repayment Reconciliation calls fail over via their circuit breakers and
every `/internal/score` call fail-safes to `MANUAL_REVIEW` — correct
behavior, not a bug. Run the root `docker-compose.yml` for real scores.

To swap in a different model, point `CREDIT_RISK_MODEL_PATH`/
`CREDIT_RISK_COEFFICIENTS_PATH` at a filesystem path and restart — no code
changes needed, since the feature set/order is driven entirely by
`coefficients.json` at runtime.

## Run tests

```bash
mvn clean verify
```

`ScoringServiceTest` covers the fail-safe paths (bureau/repayment-history
failures, missing model, malformed feature vector) and the score-band mapping
with stubbed collaborators. `OnnxModelScorerIntegrationTest` runs real ONNX
Runtime inference against a small toy model checked into
`src/test/resources/fixtures/` (generated by `generate_fixture.py`, not the
real model) to verify the tensor I/O and `output_probability`
sequence-of-maps parsing actually work against onnxruntime's real output
shape, rather than leaving that as an unverified guess.

## Known open risks, unverified

- **ONNX Runtime's multi-platform jar** is assumed to bundle `linux-aarch64`
  natives (true for `onnxruntime` — not `onnxruntime_gpu` — since roughly
  1.12), needed for this service to actually run on the target Ampere/ARM64
  host. Not yet verified inside an actual ARM64 container — check this when
  Dockerizing/deploying, per `CLAUDE.md`'s `--platform linux/arm64` rule.
- **Real skl2onnx export shape**: the output-parsing logic in
  `OnnxModelScorer` is verified end-to-end against this repo's own toy
  fixture (real ONNX Runtime inference, not a mock), which mirrors
  skl2onnx's default classifier export (zipmap on): `output_label` +
  `output_probability` as a sequence containing one `ai.onnxruntime.OnnxMap`
  per row (confirmed by inspection - it's `OnnxMap`, not a plain
  `java.util.Map`, which is easy to get wrong from the Python-side docs
  alone). If the real §12 training script exports with `zipmap=False`
  instead, `extractPositiveClassProbability`'s `float[][]` branch should
  already cover it, but that branch itself is unverified against a real
  export.
- **Service-to-service auth**: `/internal/score` is `permitAll` under the
  real (`!local`) `SecurityConfig`, since network isolation (ClusterIP, no
  Ingress) is the actual control on internal endpoints, not JWT — see that
  class's Javadoc. Worth revisiting once Keycloak's realm export and
  cross-service token propagation are actually wired up.
