- [x] Notifications Service — pure Kafka consumer per spec §4/§8/§10 (no outbox, no HTTP API beyond actuator). Two consumer classes (`ApplicationEventConsumer`, `RepaymentEventConsumer`) across all 7 topics, one shared idempotent `NotificationService.recordAndSend` backed by `notification_log` (unique constraint on `event_id` doubles as the idempotency check). v1 notifications are log-and-persist only, no real email/SMS.   - Noted a real Spring gotcha in the design doc's README: an outer `@Transactional` on `recordAndSend` around a `saveAndFlush` call that catches its own `DataIntegrityViolationException` throws `UnexpectedRollbackException` on return, because `saveAndFlush`'s own inner transactional boundary already marks the shared transaction rollback-only before the catch block runs. Fixed by removing the redundant outer `@Transactional` — the repository call already manages its own transaction.

## Known open risks, unverified
- Resilience4j: no confirmed Boot 4-compatible Spring integration module exists yet — currently using the framework-agnostic core library wired by hand instead of annotations. Worth revisiting if/when a Boot4-compatible integration ships.
- ONNX Runtime's Java artifact is assumed to bundle `linux-aarch64` natives (true for plain `onnxruntime`, not `onnxruntime_gpu`, since roughly 1.12) — not yet verified running inside an actual ARM64 container on the target Ampere host. Check this when Dockerizing/deploying the Credit Risk Engine.
- ~~The Credit Risk Engine's ONNX output-parsing... unverified against a real export.~~ Resolved: the real §12 training script (`services/credit-risk-engine/scripts/train_model.py`) also exports with zipmap on, and its self-check confirms `extractPositiveClassProbability`'s sequence-of-`OnnxMap` path matches sklearn's `predict_proba` on the real model, not just the toy fixture. The `float[][]` (`zipmap=False`) fallback branch remains unexercised — fine, since nothing now needs it.
- Credit Risk Engine's `/internal/score` is `permitAll` under its real `SecurityConfig` (network isolation, not JWT, is the control for internal-only endpoints per spec § 11) — but `HttpCreditRiskClient` in Application Service doesn't forward a JWT anyway, so this is moot until cross-service token propagation is actually designed.
- Repayment Reconciliation Service's Paddle integration has reached the real Paddle sandbox host and correctly parsed a real error response (a `403 authentication_malformed` against the `changeme` placeholder key, during the Kafka-wiring smoke test below) — but still no real API key, so a genuine successful call (customer creation, transaction/checkout) remains unverified. Worth a real end-to-end sandbox smoke test once `paddle.api-key`/`paddle.webhook-secret` are set to real values — the most likely surprise is somewhere in the checkout/subscription-activation flow, since that part can't be exercised without a frontend to complete a hosted checkout.
