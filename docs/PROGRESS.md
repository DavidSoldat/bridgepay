- [x] Mock Credit Bureau Service — stateless, no datastore. `GET /internal/bureau-profile/{applicantId}` hashes into a fixed 22,500-row in-memory pool loaded from `src/main/resources/data/bureau-pool.csv`. That pool is a real (not synthetic) held-out 15% slice of the actual Kaggle "Give Me Some Credit" `cs-training.csv` (user-provided, now at `data/cs-training.csv`, gitignored — see `data/README.md`), derived by `services/mock-credit-bureau/scripts/generate_pool.py` using a `rowIndex % 100 < 15` split rule that the future §12 training script must reuse to exclude the same rows. Compiled and verified locally (`mvn clean verify`, 7/7 tests green) with no Boot 4 issues — much smaller surface area than the other two services (no JPA/Flyway/Kafka/Redis at all). Also manually smoke-tested end-to-end (`java -jar` + `curl`) to confirm its JSON shape actually matches Credit Risk Engine's `BureauProfile` field names byte-for-byte, not just by inspection.
- [x] Trained the real credit-risk model — spec § 12. `services/credit-risk-engine/scripts/train_model.py`: applies the same `rowIndex % 100 < 15` exclusion as the bureau pool, stratified-splits the remainder into 70%/15% (of the
  original 150k) train/eval, cleans the same sentinel values/imputations as `generate_pool.py`, fits `StandardScaler` + `LogisticRegression(class_weight="balanced")` on the 10 bureau-shaped features, exports with `skl2onnx` (zipma
  p on, `target_opset=17`). AUC-ROC 0.82 on the eval split; precision/recall of 0.10/0.91 at the 0.3 threshold and 0.40/0.43 at the 0.7 threshold. Artifacts committed at `services/credit-risk-engine/src/main/resources/model/{model.
onnx,coefficients.json}`. The script self-checks that both the ONNX output and the `coefficients.json` dot product reproduce sklearn's own `predict_proba` within `1e-4` before writing anything.

r` loads the real model at startup ("`Loaded credit risk model from classpath:model/model.onnx with 10 features`"), not the fail-safe path.

- [x] Notifications Service — pure Kafka consumer per spec §4/§8/§10 (no outbox, no HTTP API beyond actuator). Two consumer classes (`ApplicationEventConsumer`, `RepaymentEventConsumer`) across all 7 topics, one shared idempotent `NotificationService.recordAndSend` backed by `notification_log` (unique constraint on `event_id` doubles as the idempotency check). v1 notifications are log-and-persist only, no real email/SMS. Compiled and verified locally (`mvn clean verify`, 11/11 tests green, real Testcontainers Kafka + Postgres, not mocks) — see `docs/superpowers/specs/2026-09-16-notifications-service-design.md` for the full design and stated deviations/assumptions (notably: `RepaymentEvents` payload shapes, including `applicantId`, are this service's own invention since Repayment Reconciliation Service doesn't exist yet to mirror).
  - This is the **first real local Kafka broker anywhere in the project** (docker-compose, single-node KRaft, official `apache/kafka` image) — not the same thing as the "wire Kafka for real across services" item below, which also needs Repayment Reconciliation's publish side. Manually smoke-tested: `docker-compose up --build`, published a real message via `kafka-console-producer.sh` to `applications.declined`, confirmed the row landed in `notification_log` and the "would send" line logged. This is also the first real proof that Application Service's outbox/Kafka producer setup and this envelope contract actually interoperate with a live broker — Application Service's own outbox poller still hasn't been run against a live broker itself, so "no broker has actually been run yet" in the item below still refers to that, not to this.
  - Noted a real Spring gotcha in the design doc's README: an outer `@Transactional` on `recordAndSend` around a `saveAndFlush` call that catches its own `DataIntegrityViolationException` throws `UnexpectedRollbackException` on return, because `saveAndFlush`'s own inner transactional boundary already marks the shared transaction rollback-only before the catch block runs. Fixed by removing the redundant outer `@Transactional` — the repository call already manages its own transaction.

## Known open risks, unverified
- Resilience4j: no confirmed Boot 4-compatible Spring integration module exists yet — currently using the framework-agnostic core library wired by hand instead of annotations. Worth revisiting if/when a Boot4-compatible integration ships.
- ONNX Runtime's Java artifact is assumed to bundle `linux-aarch64` natives (true for plain `onnxruntime`, not `onnxruntime_gpu`, since roughly 1.12) — not yet verified running inside an actual ARM64 container on the target Ampere host. Check this when Dockerizing/deploying the Credit Risk Engine.
- ~~The Credit Risk Engine's ONNX output-parsing... unverified against a real export.~~ Resolved: the real §12 training script (`services/credit-risk-engine/scripts/train_model.py`) also exports with zipmap on, and its self-check confirms `extractPositiveClassProbability`'s sequence-of-`OnnxMap` path matches sklearn's `predict_proba` on the real model, not just the toy fixture. The `float[][]` (`zipmap=False`) fallback branch remains unexercised — fine, since nothing now needs it.
- Credit Risk Engine's `/internal/score` is `permitAll` under its real `SecurityConfig` (network isolation, not JWT, is the control for internal-only endpoints per spec § 11) — but `HttpCreditRiskClient` in Application Service doesn't forward a JWT anyway, so this is moot until cross-service token propagation is actually designed.

Resolved during application-service's first `mvn clean verify` pass — see `.claude/rules/spring-boot-4-migration.md` for details: the `SecurityConfig` package paths, the `flyway-database-postgresql` question (yes, still needed alongside `spring-boot-starter-flyway`), Jackson 3 as Boot 4's default, and `RestClient.Builder` needing its own starter.

Resolved during credit-risk-engine's first `mvn clean verify` pass: Boot 4 moved `RedisCacheManagerBuilderCustomizer` (and friends) from `org.springframework.data.redis.cache` to `org.springframework.boot.cache.autoconfigure`, shipped in the new `spring-boot-cache` module — see `.claude/rules/spring-boot-4-migration.md`.
